# Task 5 — Review and refactor player registration

## Description

[PlayerController](../src/Domain/Player/Controller/PlayerController.php) handles player registration at `POST /api/players`. It works, but it was written quickly and has not been reviewed.

Your task has two parts:

1. **Review** the controller as if it were a pull request from a teammate. Point out problems in correctness, design, error handling, and testability, and explain why each one matters.
2. **Refactor** the code to fix the problems you consider most important, while keeping the behaviour described below.

There is no single correct design. Be ready to explain your choices and what you would do with more time.

## Required behaviour

Your refactored code must meet these requirements. Where the current controller does not meet one, treat it as a problem to report and fix.

### Registration

- Save a `Player` and exactly one linked `PlayerActivity` with type `player_created` and its creation timestamp.
- Save both records in one explicit Doctrine transaction. If either write fails, neither record is stored and no event is dispatched.
- After the transaction commits, dispatch `PlayerCreated` exactly once, with the saved player's generated ID, username and email.
- Send the welcome email in response to `PlayerCreated`, after the commit. If sending fails, log the failure and keep the registration successful: the records stay committed and the response is still `201`.

### Request

`POST /api/players` with a JSON object body:

| Field | Type | Rules |
| --- | --- | --- |
| `username` | string | Required. Surrounding whitespace is removed. Then 1 to 100 characters, and unique. |
| `email` | string | Required. Surrounding whitespace is removed. Then a valid email address of at most 180 characters, and unique. |

Other fields in the body are ignored.

### Responses

A successful registration returns `201` with the saved values:

```json
{"id": 1, "username": "alice", "email": "alice@example.com"}
```

The ID is generated by the database; `1` is only an example.

Errors return JSON in this shape:

```json
{"error": "A helpful error message"}
```

| Condition | Status |
| --- | --- |
| Body is not valid JSON, or is empty | `400` |
| `username` or `email` missing, not a string, or invalid | `422` |
| Username or email already taken, including a database unique-constraint conflict | `409` |
| Unexpected persistence failure | `500`, with a generic message; details go to the log |
| Email delivery fails after a successful commit | `201`; the failure is logged |

Invalid input and conflicts must not store any records or dispatch any event.

## What to deliver

- **Review notes**: a list of the problems you found, ordered by importance. For each one, say what can go wrong and how you would fix it. Note anything you chose not to change and why.
- **Refactored code** that meets the required behaviour above.
- **Checks** showing that the important behaviour works, at least:
  - a failure during either write leaves neither record in the database;
  - a duplicate username or email returns `409` and stores nothing;
  - the event is dispatched once, only after a successful commit, with the generated ID;
  - an email failure is logged and does not undo the registration or change the `201` response.

## How it is assessed

- How many real problems you find, and whether you can explain their impact.
- Whether the refactored code keeps the required behaviour.
- How responsibilities are split between HTTP handling, registration logic, and side effects.
- How errors are handled and reported, and how easy the code is to test.
- Whether your changes are proportionate: clear improvements, not rewriting for its own sake.
